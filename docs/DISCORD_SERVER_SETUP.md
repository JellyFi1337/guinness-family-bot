# Настройка Discord-сервера для Guinness Bot

Версия инструкции: 09.09.2026. Основание — фактические `bot_config.toml`, `services/provisioning.py`, `services/panels.py`, `core/permissions.py`, `services/preflight.py` и cogs.

**Сначала различайте два состояния:** сейчас бот умеет искать, привязывать и создавать объекты, но безопасное автоматическое разбиение по категориям, ACL и завершение грантов требуют R06–R09 [нового плана](IMPLEMENTATION_PLAN_V2.md). До их завершения создавайте закрытые категории/каналы вручную и выбирайте в мастере «привязать». После исправлений мастер должен предлагать проверяемое создание с правами и не дублировать объекты.

Полная последовательность запуска и ручная приёмка: [OPERATOR_RUNBOOK.md](OPERATOR_RUNBOOK.md).

## 1. Что делает человек

1. Создаёт Discord-приложение и bot user в [Developer Portal](https://discord.com/developers/applications), сохраняет токен в локальный secret-файл согласно будущему Docker quick start. Токен не пересылается в чат.
2. Включает **Server Members Intent** и **Message Content Intent** на странице Bot. Код уже запрашивает их. Отдельный Presence Intent для текущего набора intents не требуется. Назначение привилегированных intents описано в [Discord Gateway](https://docs.discord.com/developers/events/gateway).
3. На странице Installation выбирает **Guild Install** и scopes `bot`, `applications.commands`, приглашает бота на нужный сервер. Права установки и права работы — отдельные вещи. Основание: [официальное начало работы](https://docs.discord.com/developers/quick-start/getting-started).
4. Включает Developer Mode в своём Discord, копирует **Server ID** в `GUILD_ID_TEST` или `GUILD_ID_MAIN` (и `BOT_PROFILE`), **свой User ID** в `BOT_OWNER_ID` — всё в `.env`. Это разные идентификаторы. Не оставляет ID исходной гильдии в репозитории. Application ID также не является Server ID.
5. Располагает роль бота выше ролей, которые он выдаёт/снимает, включая Main/Young/Guest/Help/Contract/VIP и управляемые покупные роли. Роли людей Owner/Dep. Owner можно держать выше роли бота, если бот не должен назначать их. Человеческое назначение высших ролей остаётся у владельца.
6. Проверяет разрешения приложения на slash-команды в **Настройки сервера → Интеграции → бот**. У многих групп текущего кода стоит `default_permissions=Permissions.none()`: по умолчанию они закрыты для неадминистраторов. Разрешите нужные группы соответствующим ролям; внутренние гранты бота всё равно обязательны. Не выдавайте людям Administrator ради появления `/event` или `/contract`. [Discord command permissions](https://docs.discord.com/developers/interactions/application-commands).
7. Заполняет профиль семьи, подтверждённые улучшения, направление, лимит состава, сезон, каталоги контрактов и правила. Бот не может достоверно вывести это из наличия каналов.

Бот не создаёт сам Discord-приложение/токен, не включает intents в Portal, не приглашает себя на сервер и не может обойти Discord-иерархию ролей.

## 2. Права самого бота

Для полного текущего набора preflight проверяет:

- View Channels, Send Messages, Read Message History, Embed Links, Attach Files.
- Manage Messages, Manage Channels, Manage Roles.
- Manage Threads, Create Public Threads, Send Messages in Threads.
- Connect, Speak, Move Members для голосовых функций.

Для отслеживания приглашений/рекрутинга дополнительно нужны **Manage Server (Manage Guild)** и **Create Invite** там, где бот работает с приглашениями. На конкретных закрытых каналах нужны соответствующие channel overwrites. Глобальное разрешение не отменяет запрет на уровне канала.

Не использовать Administrator как постоянное требование установки. Если часть функций выключена после R07/R09, диагностика должна требовать только разрешения включённых функций. В текущем preflight многие проверки глобальные — это ограничение исправляется новым планом.

## 3. Категории

Названия ниже можно изменить: надёжная привязка — ID. Для быстрого ручного запуска проще оставить имена из TOML и затем сохранить IDs.

| Категория по умолчанию | Ключ ID | Для чего и кто видит |
| --- | --- | --- |
| `🌐・PUBLIC・🌐` | `CATEGORY_PUBLIC_ID` | Вход, правила, заявка в семью. Доступ гостям и кандидатам. |
| `🏠・FAMILY・🏠` | `CATEGORY_FAMILY_ID` | Семейные панели, контракты, события, помощь. Main/Young по политике семьи; не весь @everyone. |
| `🔰・HIGH TOOLS ・🔰` | `CATEGORY_HIGH_TOOLS_ID` | Служебная работа: очередь, финансы, аудит, кадровые логи. Только назначенные специалисты и руководство. |
| `🏷️・TICKETS・🏷️` | `CATEGORY_TICKETS_ID` | Создаваемые обращения. Категория закрыта; каждый тикет открывается только автору, назначенным проверяющим и боту. |
| `🕹️・INTERACTIVE・🕹️` | `CATEGORY_INTERACTIVE_ID` | Розыгрыши, опросы, магазин/игровые функции по политике семьи. |
| `✨・VOICES・✨` | `CATEGORY_VOICE_CREATE_ID` | Лобби и создаваемые временные голосовые комнаты. |
| `🌸・GROUPS・🌸` | `CATEGORY_GROUPS_ID` | Создаваемые групповые комнаты, если используются. |
| `🎂・BIRTHDAY SECRET・🎂` | `CATEGORY_BIRTHDAY_FUNDRAISER_ID` | Секретные сборы ко дню рождения. Нельзя наследовать широкую видимость. |
| `⚙️・DEVELOPER・⚙️` | `CATEGORY_DEVELOPER_ID` | Технические команды и диагностика; только владелец/техническая роль. |

Минимальный пилот использует PUBLIC, FAMILY, HIGH TOOLS и TICKETS; остальное требуется при включении соответствующих функций. До доработки optional-модулей preflight может требовать больше объектов — не исправляйте это созданием публичных пустых «служебных» каналов.

### Как вручную закрыть служебную категорию

1. В разрешениях категории запретите @everyone `View Channel`.
2. Разрешите просмотр боту и конкретным рабочим ролям. Для финансов можно создать отдельный private channel внутри HIGH TOOLS с более узкими overwrites.
3. Не выдавайте Main/Guest разрешение View на этих каналах. Проверьте другие роли тестового участника: дополнительный allow может открыть доступ.
4. Синхронизируйте дочерние каналы с категорией, кроме намеренно более узких финансовых/анонимных каналов.
5. Проверьте реальным участником без Administrator. Просмотр владельцем сервера не доказывает приватность.

## 4. Основные каналы и точные привязки

Это рекомендуемое размещение. Оно **не означает**, что текущий мастер уже автоматически выставляет parent/overwrites.

| Канал | Ключи из конфигурации | Размещение/смысл |
| --- | --- | --- |
| `старт-и-правила` | `CHANNEL_FAMILY_FEATURES_ID`; при совмещении `CHANNEL_SHOP_ID`, `CHANNEL_ADD_BIRTHDAY_ID`, `CHANNEL_VZP_ID` | FAMILY для семейных функций. Общие правила для гостей лучше отдельным сообщением в PUBLIC. В текущем registry сюда приходят `/me`, семейные панели и панель капта. Несколько ключей могут иметь **один ID**. |
| `мои-задачи` | отдельного ключа сейчас нет | Это рекомендация старого мастера, не реализованный отдельный маршрут. Пока использовать `/me` или его панель в family_features; выделение маршрута — R07. |
| `события` | `CHANNEL_SUMMIT_LIST_ID` | FAMILY: события/сборы. Новые slash-панели отвечают в канале вызова либо ephemeral; нельзя ожидать автопубликации каждого события только из-за заданного ID. |
| `отчёты` | `CHANNEL_SUMMIT_CONTRACT_ID` | FAMILY: постоянная панель каталога контрактов; сами отчёты доступны через команды и контролируемые карточки. |

| `🐳・заявки-в-семью` | `CHANNEL_FAMILY_INVITE_ID`, при совмещении `CHANNEL_RECRUITING_INVITE_ID` | PUBLIC: кандидат должен видеть вход в заявку до получения Main. |
| `📋・заявки-в-семью` | `CHANNEL_FAMILY_INVITE_LOGS_ID` | HIGH TOOLS: данные заявок и рассмотрение; только кадровики. |

| `💱・транзакции` | `CHANNEL_TRANSACTIONS_ID` | Финансовые логи, не публичный семейный чат. |

| `🚗・авто-логи` | `CHANNEL_CAR_BOOKINGS_ID` | HIGH TOOLS/логистика: выдачи/бронь/сверка. |

| `📋・выход-состава` | `CHANNEL_ROSTER_WATCH_ID` | HIGH TOOLS: разбор выхода и незакрытых обязательств. |

### Дополнительные каналы по функциям

- `🔑・роли` → `CHANNEL_ADD_ROLES_ID`, FAMILY. Заявки на роли/день рождения и одобрение можно направить в один закрытый `📝・сс-запросы`: `CHANNEL_ROLE_REQUEST_ID`, `CHANNEL_ROLE_APPROVAL_ID`, `CHANNEL_BIRTHDAY_REQUEST_ID`.
- `🎉・дни-рождения` → `CHANNEL_HAPPY_BIRTHDAY_ID`, видимость по семейной политике.
- `🎭・анон-обращения` → `CHANNEL_ANONYMOUS_REQUEST_ID`; `🕵・анон-логи` → `CHANNEL_ANONYMOUS_LOGS_ID`. Логи ограничить особенно строго; при проверке убедиться, что публичная часть не раскрывает автора через служебные поля/вложения.
- `💼・рекрутинг` → `CHANNEL_RECRUITING_ID`; `📎・рекрутинг-логи` → `CHANNEL_RECRUITING_LOGS_ID`. Рабочий кабинет рекрутеров; канал приглашения указан выше.
- `📢・новости` → `CHANNEL_WEEKLY_STATS_ID`, FAMILY или PUBLIC только после проверки состава публикуемых данных.
- `🎁・розыгрыши` → `CHANNEL_GIVEAWAYS_ID`, INTERACTIVE.
- `🌠・Create Voice +` → `CHANNEL_CREATE_VOICE_ID`, **голосовой** канал-лобби; `💤・Спальня` → `AFK_VOICE_CHANNEL_ID`, голосовой AFK. При необходимости человек отдельно выбирает серверный AFK channel в настройках Discord.
- API по желанию: `📈・рейтинг` → `CHANNEL_INSIGHTS_RATING_ID`, `📋・разборы` → `CHANNEL_INSIGHTS_BATTLES_ID`, `🛒・рынок` → `CHANNEL_INSIGHTS_MARKET_ID`, `🏠・псн` → `CHANNEL_INSIGHTS_PROPERTY_ID`. Без ключа/настроек источник не работает и панели не считаются обязательными.
- Архивные маршруты `CHANNEL_SUMMIT_VZP_ID` (`архив-сборов`) и `CHANNEL_VZP_INVITE_ID` оставлены для совместимости. На новом сервере не создавать архив ради зелёной проверки. Сохранение истории в БД не требует публичного архивного канала.

## 5. Роли и три независимых уровня доступа

Есть **Discord permissions** (видимость/действия бота), **доступ к slash-командам в Integrations** и **внутренние Permission grants** на role_id. Также есть запись участника и его игровые допуски. Одно не заменяет другое.

### Роли, которые знает конфигурация

- `Owner` → `OWNER_ROLE_ID`; `Dep. Owner` → `DEP_OWNER_ROLE_ID`.
- `High` → `HIGH_ROLE_ID` и `STAFF_ROLE_ID`. Обычно это **одна роль с одним ID**, не две High.
- `Guest` → `GUEST_ROLE_ID`, кандидат/гость; `Young` → `YOUNG_ROLE_ID`, испытательный состав; `Main` → `MAIN_ROLE_ID`, основной состав.
- `Friend`, `Super Friend` → `FRIEND_ROLE_ID`, `SUPER_FRIEND_ROLE_ID`, если эти статусы реально используются.
- `Help`, `Contract` → `HELP_ROLE_ID`, `CONTRACT_ROLE_ID`, подписки/оповещения по процессу. Подписка не даёт права принимать отчёты и выдавать имущество.
- `🪙 VIP` → `VIP_ROLE_ID`, магазин при использовании.
- `VZP Team`, `Lead VZP`, `[1] VZP`, `[2] VZP`, `[3] VZP` — устаревшие lookup-алиасы. На новой гильдии не создавать. В существующей не удалять автоматически без проверки использования другими средствами.

### Минимальные внутренние полномочия специалистов — целевая схема

Дополнительные роли «Кадровик», «Проверяющий», «Командир», «Казначей», «Снабженец» можно создать вручную. Они должны назначаться через поддерживаемый интерфейс grants после R06–R09; не вставлять SQL вручную. Текущий мастер работает с каноническими role keys и не является универсальным редактором любых специализированных ролей — это нужно довести в R09.

| Работа | Внутренние grants |
| --- | --- |
| Кадровик | MEMBERS_VIEW, MEMBERS_MANAGE, APPLICATIONS_REVIEW |
| Наставник/учебный состав | MEMBERS_VIEW, TRAINING_MANAGE |
| Проверяющий отчёты | REPORTS_REVIEW; QUEUE_ASSIGN только если назначает чужие задачи |
| Управляющий контрактами | CONTRACTS_MANAGE |
| Командир | EVENTS_CREATE, EVENTS_MANAGE_OWN; EVENTS_MANAGE_ALL только координатору всех событий |
| Просмотр финансов | TREASURY_VIEW |
| Согласующий | TREASURY_VIEW, TREASURY_APPROVE |
| Плательщик/сверка | TREASURY_VIEW, TREASURY_PAY |
| Снабженец | INVENTORY_MANAGE, VEHICLES_MANAGE по своей работе |
| Развитие семьи | PROGRESSION_MANAGE |
| Аудитор | AUDIT_VIEW; остальные права только по необходимости |
| Администратор конфигурации | CONFIG_MANAGE |

Текущий автоматический посев шире этой минимальной схемы: роли `HIGH_TOOLS_ALLOWED_*` получают большой staff bundle, Owner дополнительно treasury bundle. High не получает TREASURY_APPROVE/PAY из staff bundle. Не проверяйте разделение обязанностей аккаунтом Owner со всеми правами.

Дополнительно проверьте `[access]`: `HIGH_TOOLS_ALLOWED_ROLE_IDS`, `REQUEST_PING_ROLE_IDS`, `TREASURY_OWNER_ROLE_ID`, `POLL_ALLOWED_ROLE_IDS`, `RECRUITING_ROLE_IDS`, `TICKET_ASSIGNMENT_ROLE_HIERARCHY_IDS`. Это не канонические `*_ROLE_ID`; заполнение Main/High само по себе не гарантирует заполнение всех этих списков.

## 6. Применение настройки

1. Запустите тестовый bot с правильными GUILD_ID/BOT_OWNER_ID и дождитесь синхронизации команд.
2. До исправления bootstrap создайте High вручную, назначьте себе, убедитесь в корректности `[access]` и выполните один перезапуск для первоначального посева. Это временный путь текущего кода. После R06 проверяется запуск owner на полностью пустой структуре без этого обхода.
3. Выполните `/setup start`. Пройдите профиль → структура → роли → полномочия → панели → итог. Для уже созданного объекта выбирайте привязку по ID; не нажимайте создать для каждого алиаса.
4. Проверьте предпросмотр. После R07 он должен показывать parent/visibility, после R08 — корректно завершать отложенное создание. Пока этих изменений нет, не доверяйте слову «закрытый» в описании.
5. Выполните `/setup status`, `/config diff`, `/config export`. Runtime ID находятся в PostgreSQL, а не обязательно в TOML. Экспорт публичной конфигурации храните вместе с эксплуатационной копией; формат импорта должен быть документирован исполнителем R21.
6. Выполните `/admin preflight` и разберите **каждую** критичную строку. `/admin config_ids` помогает собрать IDs, но после R09 сверяйте его с effective runtime configuration.
7. `/panels list` показывает реальные ключи панелей. Для выбранной панели используйте `/panels deploy`, `/panels repair` или `/panels redeploy` с параметрами из Discord picker. `/admin setup` — массовая публикация старого механизма, не замена полному мастеру структуры.
8. Зайдите под Guest/Main и специалистами, проверьте видимость/команды/кнопки. Только после этого приглашайте обычных участников.

Создание временных тикетов, voice-комнат, групп, сообщений и веток выполняют соответствующие процессы бота при действиях пользователей. Статические категории, лобби и маршруты всё равно должны быть настроены заранее. Нельзя обещать, что один `/setup` текущей версии уже полностью подготовит все такие процессы.
