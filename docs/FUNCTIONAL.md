## 1. Как читать этот документ

Бот почти не использует текстовые префикс-команды. Пользователь действует через:

| Способ | Когда | Пример |
| --- | --- | --- |
| Постоянная панель с кнопкой | Повседневные заявки, роли, магазин, казна, автопарк | «Подать заявку в семью» |
| Slash-команда `/группа действие` | Создание событий, управление, админка | `/event create` |
| Модальная форма Discord | После кнопки или селектора | заявка в семью, текст обращения |
| Кнопки на живом сообщении | Сборы, тикеты, розыгрыши, плеер | «Участвовать / выйти» |

Ответы команд, как правило, **ephemeral** — видны только вызвавшему. Публичный результат появляется в тематическом канале.

Обозначения в таблицах:

- `<параметр>` — обязательный;
- `[параметр]` — необязательный;
- **доступ** — кто проходит проверку Discord/бота (владелец бота проходит почти все проверки команд, см. [§4](#4-модель-доступа)).

## 2. Что делает бот

Guinness Bot обслуживает **один** Discord-сервер (`GUILD_ID` в `bot_config.toml`). Взаимодействия с других серверов отклоняются, с чужих гильдий бот выходит.

Основные блоки:

1. Заявки в семью, в боевую команду, дни рождения, роли.
2. Обращения к старшему составу: тикеты и анонимная переписка.
3. Казна семьи и журнал транзакций.
4. События Memphis, семейные контракты, каталог карт.
5. Личная панель участника и панель старшего состава.
6. Автопарк и бронирование машин.
7. Внутренняя валюта Guinn Coins, магазин, VIP, платная музыка.
8. Недельная статистика Discord и онлайн игрового сервера.
9. Рекрутинг по персональным приглашениям.
10. Розыгрыши, опросы, закрытые сборы на дни рождения.
11. Служебные команды владельца: диагностика, Showdown, очистка сервера.

## 3. Как исполняется действие

### 3.1. Цепочка slash-команды

```text
Пользователь вводит /coins daily
        │
        ▼
Discord Application Command → interaction
        │
        ▼
core/command_tree.py
  • сервер = GUILD_ID?
  • бот не в режиме обслуживания?
        │
        ▼
Проверки команды (роль, cooldown discord.py)
  • владелец бота (BOT_OWNER_ID) обходит эти проверки
        │
        ▼
Обработчик в cogs/*.py
  • валидация данных (баланс, канал, владелец объекта)
  • запись в PostgreSQL через repositories/ или utils/database.py
  • ответ через ui/messages.py (Components v2)
        │
        ▼
При необходимости: outbox (services/operation_worker.py)
  повторяет публикацию в Discord после сбоя
```

Важно: **обход владельца бота не отменяет бизнес-правила**. Нельзя перевести себе монеты, забронировать занятую машину или управлять чужой голосовой комнатой только потому, что вы владелец бота. Обходятся только `app_commands.check` и Discord-cooldown команды.

### 3.2. Цепочка кнопки постоянной панели

```text
Кнопка с постоянным custom_id (например family_btn)
        │
        ▼
View зарегистрирован при старте: bot.add_view(...)
        │
        ▼
Открывается модалка / селектор
        │
        ▼
on_submit: номер заявки → запись в БД → карточка в канал СС
        │
        ▼
Кнопки одобрения/отказа на карточке (тоже persistent custom_id)
```

Постоянные `custom_id` нельзя менять без миграции: после перезапуска старые сообщения должны продолжать работать. Новые панели создаёт `/admin setup`. Структуру сервера раскладывает `/setup start`.

Новые постоянные списки и вкладки (реестр состава, очередь, события) кодируют страницу, фильтр и владельца в схеме `g:<версия>:<домен>:<действие>:<id>:<параметры>` (`ui/custom_ids.py`). Навигация — `ui/navigation.py` (`Paginator`, `TabbedPanel`, `FilterBar`, `ConfirmDialog`); состояние не хранится в словарях процесса. После перезапуска кнопки подхватывает `register_navigation` в `setup_hook`. Персональный ephemeral-список по-прежнему `ui/pagination.py:EphemeralPager` — его память сбрасывается вместе с сообщением, пользователь просто повторяет команду. Неизвестная версия `custom_id` отвечает «кнопка устарела», а не молчит.

### 3.3. Слои кода

| Слой | Каталог | Ответственность |
| --- | --- | --- |
| Точка входа | `main.py`, `core/bot.py` | запуск, intents, загрузка cog, sync команд |
| Команды и события | `cogs/` | Discord: команды, кнопки, listener’ы |
| Сценарии | `services/` | outbox, панели, кулдауны, метрики, preflight, журнал решений |
| Данные | `repositories/` | SQL конкретной предметной области |
| Совместимый SQL | `utils/database.py` | старые доменные операции, ещё не вынесенные |
| UI | `ui/` | Components v2, тексты команд, шаблоны ответов |
| Конфиг | `bot_config.toml`, `.env`, `config.py`, `core/profile.py`, `core/settings.py`, `core/permissions.py`, `core/logging_setup.py` | каналы, роли, цены, карты, профиль, live-настройки, полномочия, лог, срок хранения журнала |

Правило правок: **не писать SQL внутри кнопки**. Меняете хранение — `repositories/`. Меняете текст карточки — `ui/` или embed-хелперы в cog. Меняете сценарий — cog + при необходимости сервис.

### 3.4. Реестр имён команд

Любая подсказка вида «используйте `/coins daily`» должна ссылаться на `ui/command_registry.py`. Тест сверяет реестр с живым деревом команд. Переименовали команду в cog — обновите `COMMANDS` в реестре, иначе CI упадёт, а в текстах останутся мёртвые ссылки.

## 4. Модель доступа

Реализация: `core/permissions.py`, `utils/access.py`. Списки ролей — секция `[access]` в `bot_config.toml`. Если заполнен `*_ID`, имя роли не даёт прав. Именованные полномочия выдаются **роли** в `permission_grants`, не человеку и не в toml.

Доменное действие проходит четыре проверки: активное членство (пока «есть игровая роль», полный реестр в 4.2), предметное полномочие, область действия, актуальный допуск (пока всегда да, полный контроль в 4.4). Подписка на `Contract` или боевые оповещения полномочия не даёт.

| Уровень | Кто | Что даёт |
| --- | --- | --- |
| Владелец бота | `BOT_OWNER_ID` | все slash-команды и компоненты; обход cooldown команд; доступ в режиме обслуживания; обход проверки команды пишется в `decision_log` как `owner_bypass` |
| Discord Administrator | право Administrator на сервере | только эксплуатационные команды (`/admin`, `/dev`, `/car`, `/coins grant`, …). Доменные действия Administrator само по себе не открывает |
| Старший состав (staff) | роли из `HIGH_TOOLS_ALLOWED_ROLE_IDS` / имён | обработка заявок в HIGH TOOLS, тикеты, розыгрыши, опросы (если совпадает список), музыка pause/disconnect, `/help cooldown`; при первом запуске эти роли получают набор доменных полномочий старшего состава |
| Рекрутер | `RECRUITING_ROLES` | персональная ссылка и отчёт рекрутинга |
| Создатель опросов | `POLL_ALLOWED_ROLES` | `/poll create` |
| Владелец казны | `TREASURY_OWNER_ROLE` | `/admin treasury_set` |
| Владелец голосовой комнаты | user id в БД комнаты | `/voice *` и кнопки панели комнаты |
| Инициатор сбора / контракта | автор списка | карта и утверждение на архивных кнопках; новые события — `/event create` |
| Активный VIP | запись VIP в экономике | до 3 купленных ролей, `/coins role_order`, постоянный voice ban-лист |
| Обычный участник | все остальные | панели, `/help`, `/coins` (кроме grant/take/reset), `/stats weekly`, музыка play |

Проверка заявок в категории старшего состава: роли `HIGH_TOOLS_ALLOWED_*`. При новой заявке пингуются `REQUEST_PING_ROLES`.

Иерархия назначения тикета: `TICKET_ASSIGNMENT_ROLE_HIERARCHY` сверху вниз. Нельзя назначить человека с более высокой учитываемой ролью.

## 5. Постоянные панели и кнопки

Создаются и обновляются командой `/admin setup` (`cogs/admin.py` → `cogs/interactions.py` → `setup_all_persistent_messages`). Каналы, роли и профиль раскладывает `/setup start`. Повторный вызов не должен плодить копии: панель ищется по `(guild_id, panel_key)` и скрытому marker.

Несколько панелей могут жить в `старт-и-правила`. Порядок в общей панели: магазин → день рождения → заявка в боевую команду → помощь. Мастер `/setup start` по умолчанию предлагает каналы `старт-и-правила`, `мои-задачи`, `события`, `отчёты`, `помощь` и закрытые `очередь-сс`, `выплаты`, `снабжение`, `аудит`.

### 5.1. Панели `/admin setup`

| Панель | Канал (ключ конфига) | Кнопки / поведение | Код |
| --- | --- | --- | --- |
| Поддержка семьи | `CHANNEL_HELP` | **Нужна помощь** → форма | `PersistentHelpButton` |
| Обращение к СС | `CHANNEL_REQUEST_SS` | **Отправить обращение** → выбор типа | `PersistentSSButton` |
| Заявка в боевую команду | `CHANNEL_VZP` | **Оставить заявку в боевую команду** | кнопка в `cogs/forms.py` |
| Заявка в семью | `CHANNEL_FAMILY_INVITE` | **Подать заявку в семью** | `PersistentFamilyButton` |
| Роли и доступы | `CHANNEL_ADD_ROLES` | Guest / Help / Contract + заявки Young/Main и Friend | `AddRolesView` |
| Календарь ДР | `CHANNEL_HAPPY_BIRTHDAY` | список дат; кнопка полного списка | `BirthdayListView` |
| Добавить ДР | `CHANNEL_ADD_BIRTHDAY` | **Добавить свой день рождения** | `PersistentBirthdayButton` |
| Казна | `CHANNEL_TREASURY` | **Пополнение** / **Снятие** | `TreasuryView` |

| Рекрутинг | `CHANNEL_RECRUITING` | отчёт (создаётся setup + `RecruitingCog.refresh_stats`) | `cogs/recruiting.py` |

### 5.2. Форма «Нужна помощь»

**custom_id кнопки:** `help_request_btn`.

Поля модалки (`HelpRequestModal`):

- вид помощи (до 500 символов);
- до 5 изображений (только image/*, файл ≤ 8 МБ, сумма ≤ 20 МБ).

Исполнение:

1. Кулдаун `help_request` (по умолчанию 300 с, старший состав и владелец бота без ожидания).
2. Номер `HR-NNNN`.
3. Публикация в `CHANNEL_HELP_TARGET` с упоминанием роли Help.
4. Сразу создаётся ветка `помощь-hr-…`, автор добавляется в ветку.
5. Запись в журнал заявок.

Где менять: `cogs/forms.py` (`HelpRequestModal`), кулдаун — `[cooldowns]` или `/help cooldown`.

### 5.3. Обращение к старшему составу

**custom_id кнопки:** `ss_request_btn` → селектор `ss_type_select` → модалка с текстом (до 2000).

| Тип | Что создаётся | Кто видит канал | Пинг |
| --- | --- | --- | --- |
| Жалоба | приватный тикет `жалоба-username-NNNN` | автор + роли ping СС | СС |
| Предложение | тикет `предложение-…` | то же | СС |
| Owner-request | тикет | автор + роль Owner (+ админы Discord по правам) | роль Owner |
| Обращение по работе бота | тикет | автор, Discord-админы, владелец бота; отсутствие владельца на сервере не блокирует создание | упоминание `BOT_OWNER_ID` |
| Анонимный запрос | **не тикет** | публичная карточка без автора + закрытый лог | см. §7.2 |

Кнопки тикета (`TicketCloseView`, persistent):

- **Взять тикет** / **Сняться с тикета** (`claim_ticket`);
- **Назначить на тикет** — выбор сотрудника;
- **Закрыть тикет** — автор или СС.

После закрытия канал удаляется через outbox (`ticket.delete_channel`), статистика закрытия уже записана.

Где менять типы: `SSRequestTypeSelect` в `cogs/forms.py`. Права канала: `_ticket_overwrites`.

### 5.4. Заявка в семью

**custom_id:** `family_btn`.

Поля:

- OOC имя и возраст;
- IC имя;
- идентификатор персонажа Memphis (паспорт другого проекта не подставляется);
- кто пригласил;
- смена фамилии — политика Guinness (`off` / `ask` / `required`);
- специализация (боевой состав / логистика / контракты / наставничество);
- прайм только Пн/Ср/Пт/Сб.

Исполнение:

1. Номер `FI-NNNN`, payload в БД. На карточке — сезонная отсечка: 28 дней до конца сезона и 30+ часов (часы не подтверждены до 9.1).
2. Карточка в `CHANNEL_FAMILY_INVITE_LOGS` с пингом СС.
3. Кнопки: **Принять в кандидаты**, **Пригласить на собеседование**, **Запросить ник**, **Отклонить**. Старые `custom_id` сохранены.
4. Принятие заводит **кандидата** и маршрут адаптации. Это не членство в организации; в игре — `/members verify`.
5. Собеседование оставляет заявку открытой. Решение не выдаёт Main и общие права администратора.
6. Запрос ника: автору в ЛС кнопка подтверждения формата `Имя в игре | Имя в реале`.
7. Рекрутинг: подача помечается; **зачёт принятых** — после одобрения; `verified_at` — после подтверждения в игре; `retained_at` — если задан `ONBOARDING_RETENTION_DAYS`.

Где менять поля: `cogs/applications.py` (`FamilyInviteModal`). Решение: `FamilyApprovalView` там же. Кнопка панели по-прежнему `PersistentFamilyButton` в `cogs/forms.py`.

### 5.5. Заявка в боевую команду

**custom_id:** `vzp_btn`.

Поля: IC имя-фамилия, опыт.

Карточка в очередь старшего состава. Кнопки:

- одобрить (боевая роль сервера);
- одобрить и выдать одну из устаревших приоритетных ролей, если они ещё есть на сервере;
- отклонить.

Где менять: модальное окно и кнопки решения в `cogs/forms.py`. Новые номера заявок — префикс `BT`.

### 5.6. День рождения

**custom_id:** `birthday_btn`. Дата `ДД.ММ`.

После одобрения запись попадает в единое сообщение календаря. Админ может обойти заявку: `/admin birthday_add` / `birthday_remove`.

### 5.7. Панель ролей

| Кнопка | Поведение |
| --- | --- |
| Guest | выдать / снять сразу |
| Help | выдать / снять сразу |
| Contract | сразу, только если есть Young, Main, Senior Staff, High или Owner |
| Young / Main | селектор уровня → форма → карточка на согласование; проверяющий может выдать любой из двух уровней |
| Friend / Super Friend | аналогично |

Кастомная роль из магазина согласовывается отдельно (кнопки `role_approval:approve` / `reject`).

### 5.8. Казна (кнопки)

`treasury_deposit` / `treasury_withdraw` открывают форму: сумма + причина. Пишется транзакция **старой** модели `treasury`, обновляется одно сообщение казны, в `CHANNEL_TRANSACTIONS` уходит карточка. Абсолютный баланс старой модели — `/admin treasury_set` (роль владельца казны). Обычное движение старой модели — ещё и `/admin transaction_add`. Новые выплаты и сверка с игрой — `/treasury`. Панель показывает время последней сверки, если она уже записана.

### 5.9. Магазин (кнопки)

| custom_id | Действие |
| --- | --- |
| `shop:color_role` | купить цветную роль «Цвет» (HEX; градиент при `ENHANCED_ROLE_COLORS`) |
| `shop:custom_role` | заявка названия → СС в role-approval → создание роли |
| `shop:vip` | неделя или месяц |
| `shop:emoji` | VIP-эмодзи для списков сборов/контрактов |
| `shop:sell_role` | продажа купленной роли, возврат 50% |

Лимиты: без VIP — 1 цвет + 1 кастом; с VIP — до 3 ролей. Одинаковый HEX переиспользует существующую Discord-роль. По окончании VIP лишние роли снимаются с возвратом 50%, ban-лист голоса чистится.

Цены: `[economy]` в `bot_config.toml`. Логика: `cogs/shop.py`.

## 6. Справочник slash-команд

Команды синхронизируются **только на гильдию** `GUILD_ID`. В личке недоступны.

Группы сами по себе не вызываются: Discord показывает подкоманды.

### 6.1. `/help` — справка

| Команда | Доступ | Параметры | Исполнение |
| --- | --- | --- | --- |
| `/help overview` | все | `[аудитория]` участник или старший состав | ephemeral Components v2; только функции активного профиля; кулдаун `help` (по умолчанию 5 с) |
| `/help cooldown` | СС | `<команда>` `<секунды>` 0–86400 | пишет кулдаун сервера в БД |

Настраиваемые кулдауны: форма помощи, справка, создание события, запуск контракта, обычный сбор.

### 6.2m. Заслуги (внутренний вклад)

Непередаваемая единица **заслуги**. Это не Dark Coins, не Guinn Coins и не семейный счёт вклада из `/treasury`. Начисляются только за подтверждённый результат: принятый отчёт, явка командиром, закрытое обучение новичка (наставнику). Склад, логистика и дежурство ждут своих модулей. Файлы: `services/contribution.py`, `repositories/contribution.py`. Показ — вкладка «Мой прогресс» в `/me`.

### 6.2p. `/progress` — развитие семьи и сезонное право

## 7. Подсистемы подробно

### 7.1. Согласование заявок (общий паттерн)

1. Пользователь отправляет форму.
2. `get_next_number(префикс)` — человекочитаемый номер.
3. `log_request` сохраняет автора, тип, payload.
4. Карточка в канал очереди + persistent View одобрения.
5. Решение: роли, ЛС автору, карточка в `CHANNEL_REQUEST_ACTIONS` (СС-логи).
6. При сбое публикации решение догоняется outbox `request.present`.

Отказ: причины из `ROLE_REJECTION_REASONS` (разделитель `|`) для ролей магазина; для заявок — аналогичный выбор/текст в формах отклонения.

### 7.2. Анонимные обращения

Не создаёт тикет-канал.

1. Публичная карточка в `CHANNEL_ANONYMOUS_REQUEST` без автора.
2. Закрытая копия автора в `CHANNEL_ANONYMOUS_LOGS`.
3. Кнопки СС на публичной карточке и в ветке: ответить / закрыть.
4. Ответ СС → ЛС автору (кнопки ответить / закрыть).
5. Ответ автора → обратно в ветку без раскрытия личности.
6. Связи сообщений в `repositories/anonymous.py`, переживают рестарт.

Файл: `cogs/anonymous_relay.py`, создание — ветка в `cogs/forms.py`.

### 7.3. Архивные сборы: жизненный цикл после 10.2

```text
старт SummitsCog
    → archive_open_legacy_gatherings (vzp_gathering и kind=contract)
    → состав и позиции не удаляются, archived_at + is_open=0
    → outbox summit.archive уведомляет канал и инициатора
    → старые кнопки отвечают SUMMIT.ARCHIVED
    → дальше: /event create, /event list, /contract start
```

Карты: таблица `family_maps`, заполняет старший состав через `/event map_add` (версия, тип события, источник). Пустой каталог допустим. Discord Select показывает не больше 25 пунктов на странице; страниц может быть несколько. Старые изображения площадок из репозитория удалены.

### 7.4. Экономика Coins

Источники:

| Источник | Когда | Идемпотентность |
| --- | --- | --- |
| daily | `/coins daily` | один раз на дату MSK |
| pay | перевод | списание+зачисление в одной транзакции |
| admin_* | grant/take/reset | прямая корректировка |
| message | listener сообщений | cooldown + daily cap + исключённые каналы |
| voice | periodic accrual | минуты активности, daily cap |
| shop | покупка | списание до выдачи роли; outbox на создание роли |
| music | play | списание после extract; refund по правилам skip/crash |

Дробные награды копятся в milli-coins и округляются при выплате.

### 7.5. Статистика недели

События (сообщения, voice join/leave, тикеты, заявки, запуски сборов) идут в очередь → пачки в PostgreSQL. Сырьё хранится `STATS_RAW_RETENTION_DAYS` (90), агрегаты — `STATS_AGGREGATE_RETENTION_DAYS` (730). Heartbeat открытых voice-сессий раз в 60 с, чтобы рестарт не раздувал длительность.

Онлайн игрового сервера выбирается профилем `online_source`: `none` (семейный статус, master-list не вызывается), `rage_master` (архивный master-list предыдущего проекта, текущая логика RAGE) или `majestic_api` (официальный API, только после заполнения `[external]` и `MAJESTIC_API_KEY`). Ошибка или таймаут не подменяются нулём: показывается «онлайн недоступен» или последний достоверный снимок с отметкой времени. Дневной агрегат пишется только по свежему успешному числу.

Панели рейтинга, разборов, рынка и ПСН (`/panels`) читают каталог API, а не онлайн-источник профиля. У каждой карточки подпись источника и время. Сбой обновления показывает последний снимок («обновление не удалось, показаны данные от ЧЧ:ММ»), а не нули. Сводки по игрокам чужих семей не строятся.

### 7.6. Надёжность Discord ↔ БД

Discord и PostgreSQL не в одной транзакции. Критичные шаги:

- `operation_outbox` + `idempotency_key`;
- `command_receipts` на денежные команды;
- покупка роли: сначала Discord role id, потом финализация;
- продажа роли и отказ кастома: возврат 50% и карточка восстанавливаются из outbox;
- победители розыгрыша фиксируются **до** публикации.

Если меняете денежный или ролевой сценарий — сохраните этот паттерн, иначе после рестарта появятся двойные роли или двойные списания.

### 7.7. Схема семьи и состава

Таблицы `family_context`, `members`, `ranks`, `clearances`, `member_events` (миграция 36) — пустые: данные предыдущего проекта не переносятся.

- Одна активная `family_context` на гильдию; архивные строки остаются.
- Участник ищется по `discord_id` внутри семьи, не по нику. Одинаковый `game_character_id` на другой семье — другой человек.
- Текущее выбранное членство на `(family_id, discord_id)` одно. Второй персонаж — отдельная строка с `is_selected = 0`.
- Статусы: `candidate`, `probation`, `active`, `leave`, `left`. Ушедших не удаляют: `left` + событие в `member_events`.
- `ranks` — внутренние должности; `discord_role_id` только связь. Игровой ранг сюда не пишется.
- Лимит состава для проверки берётся из профиля (`ServerProfile.member_limit`), не из зашитого числа. Пока лимит не задан, проверка не подставляет 150.
- Реестр и карточка — `/members` (`services/membership.py`). Кандидат становится `active` только после `/members verify`.
- Личная панель — `/me` и кнопка на панели `me` в `family_features`.

Файлы: `repositories/family.py`, `repositories/members.py`, `services/membership.py`, `cogs/members.py`, `services/member_panel.py`, `cogs/member_panel.py`.

| `recruiting` periodic | (в cog) | инвайты и отчёт |

Падение одной итерации: backoff, запись в `task_health`, бот не останавливается.

## 10. Типичные изменения

### Добавить slash-команду в существующую группу

1. Метод с `@app_commands.command` в GroupCog.
2. Строка в `COMMANDS` (`ui/command_registry.py`).
3. При пользовательской подсказке — `cmd("group name")`, не голая строка.
4. Перезапуск; при кэше схемы — `COMMAND_SYNC_FORCE=true` на один запуск.

### Переименовать команду

1. `name=` в cog.
2. Реестр.
3. Поиск старого qualified name в help-текстах и README.

### Сменить, кто создаёт опросы / розыгрыши / рекрутит

Списки `POLL_ALLOWED_*`, `HIGH_TOOLS_ALLOWED_*`, `RECRUITING_*` в `bot_config.toml`. Предпочтительно ID. Затем `/admin preflight`.

### Добавить карту

`/event map_add` с названием, типом события, версией и источником. Каталог не ограничен 25 записями. Совпадение названия местности с другой игрой не доказывает совпадение карты.

### Изменить воронку рекрутинга

Сейчас зачёт = одобренная семейная заявка. Логика в `record_family_application` / `decide_recruiting_referral` (`cogs/recruiting.py`, `utils/database.py`, `repositories/recruiting.py`). Если нужно зачитывать приглашение без заявки — это сознательная смена бизнес-правила, не «мелочь в команде».

### Выключить пассивные Coins за сообщения

`/stats economy_config message_reward:0` или `COINS_MESSAGE_REWARD = 0` и рестарт. Исключить каналы: `COINS_MESSAGE_EXCLUDED_CHANNEL_IDS`.

### Новая постоянная панель

1. View с `timeout=None` и стабильным `custom_id`. Для нового листа/вкладок — `Paginator` / `TabbedPanel` и схема `g:` из `ui/custom_ids.py`, не словарь в памяти.
2. `bot.add_view` в `InteractionsCog.cog_load` для уже существующих панелей; новые `g:`-кнопки после рестарта обрабатывает `register_navigation`.
3. Вызов `_provision_panel` в `setup_all_persistent_messages`.
4. Канал в `[channels]`.

### Опасные команды

`/dev_reset_server` и `/showdown toggle` рассчитаны на владельца бота. Скрытые описания (`.`) не отменяют доступность в дереве команд для тех, кому Discord их показывает. Не выдавайте боту лишние права Manage Server без необходимости wipe-сценариев.

## 11. Конфигурация, влияющая на поведение

Секреты только в `.env` (`TOKEN`, `DATABASE_URL`, `MAJESTIC_API_KEY`). Поведение и маршруты — `bot_config.toml`.

| Секция | Влияет на |
| --- | --- |
| `[discord]` | гильдия, владелец, sync команд |
| `[profile]` | проект, сервер, семья, направление, сезон, открытые улучшения, лимит состава, нейтральные ключи архивного RAGE |
| `[status]` | присутствие Discord; игровой онлайн только если профиль выбрал источник |
| `[external]` | URL, версия, serverId, лимит N/M и подпись API Majestic; пусто — интеграция выключена |
| `[channels]` / `[categories]` | куда что публикуется |
| `[roles]` | какие Discord-роли выдаёт бот |
| `[access]` | кто СС, кто казна, кто опросы, иерархия тикетов, причины отказа |
| `[economy]` | цены магазина, daily, пассивные Coins |
| `[treasury]` | `TREASURY_BATCH_THRESHOLD` — порог пакета; 0 значит пакет выключен |
| `[contribution]` | заслуги по категориям; 0 — правило не задано, начисления нет |
| `[bonus]` | премия периода: вид, порог, потолок доли, влияние и справочник рангов |
| `[inventory]` | ёмкости склада, сейфа, шкафа, кладовой, гаража и матовозки; порог запаса и сверки 0 — не заданы |
| `[progression]` | сезонное право (28 дней / 30 часов), перерыв смены направления, потеря репутации в тысячных, максимум уровней |
| `[music]` | цены, очереди, skip, ffmpeg, хосты |
| `[cooldowns]` | стартовые значения (дальше живут в БД после `/help cooldown`) |
| `[database]` | пул, очереди статистики, TTL, `AUDIT_RETENTION_DAYS` |
| `[logging]` | формат и уровень лога; `LOG_DIR` пуст — только stdout/journald |

Секции `[channels]`, `[categories]`, `[roles]`, `[access]`, `[economy]`, `[cooldowns]`, `[profile]` и `[external]` можно переопределить на работающем боте через `runtime_settings` (`core/settings.py`). `AUDIT_RETENTION_DAYS` тоже живой. Запись live-настройки и строка `decision_log` идут в одной транзакции. Полномочия ролей — таблица `permission_grants`, не toml. `TOKEN`, `DATABASE_URL`, `MAJESTIC_API_KEY`, `GUILD_ID`, `BOT_OWNER_ID`, `DB_POOL_SIZE` и пути по-прежнему требуют перезапуска. Служебные ключи панелей остаются в `guild_settings` и не смешиваются с пользовательскими настройками.

После правки toml/env нужен **перезапуск**, кроме runtime-настроек выше, ставок экономики через `/stats economy_config` и правок через `/config set` (кроме `restart_required`).

Проверка маршрутов на живом сервере: `/admin preflight`. Выгрузка актуальных значений: `/config export` (`/admin config_ids` — устаревший синоним).
